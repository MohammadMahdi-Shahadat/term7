تا این‌جا یاد گرفتیم ویژگی بسازیم. سؤال این جلسه سخت‌تر است: آیا می‌شود به عددی که مدل گزارش می‌کند اعتماد کرد؟ یک AUC برابر ۰٫۹۶ ممکن است فقط یک باگ باشد که لباس موفقیت پوشیده. این‌جا یاد می‌گیری تقسیم داده را مثل یک «شبیه‌سازی استقرار» طراحی کنی و نشت را قبل از این‌که مدیرت را گول بزند پیدا کنی.

۱ کجای درس هستیم؟ از «ویژگی بسازیم» به «به عدد اعتماد کنیم» اسلاید

نقشه‌ی درس هفت ایستگاه دارد: فهم مسئله ← آماده‌سازی داده (پاک‌سازی و کدگذاری) ← EDA (پیدا کردن الگو) ← مهندسی ویژگی (مقیاس و تبدیل) ← کاهش بعد (نمایش بهتر) ← آماده‌سازی برای مدل ← مدل‌های یادگیری ماشین. اسلاید ۰۶ همان ایستگاه ششم است: train/validation/test، داده‌ی نامتوازن، pipeline و اعتبارسنجی متقاطع. خروجی کل این مسیر به زبان اسلاید: «از داده به بینش و پیش‌بینی، با یک فرایند ساخت‌یافته و بازتولیدپذیر».

جمله‌ی کلیدی جلسه
«یک نمایش خوب هنوز یک آزمایش قابل‌اعتماد نیست.» (A good representation is not yet a trustworthy experiment.)
امروز از سؤال «Can we build features?» به سؤال «Can we believe the score?» می‌رویم.

اسلاید اهداف یادگیری را با یک جمله شروع می‌کند: «دانشجو باید بتواند طراحی را توضیح دهد، نه فقط Python اجرا کند». پنج هدف اسلاید این‌هاست:

سازمان سخنرانی هم پنج بخش دارد: ۰۱ تقسیم معتبر (train / validate / test) ← ۰۲ اعتبارسنجی متقاطع (استقلال و واریانس) ← ۰۳ ممیزی نشت (جلوگیری از اطمینان کاذب) ← ۰۴ رویداد نادر (معیار، هزینه، کالیبراسیون) ← ۰۵ pipeline (آزمایش بازتولیدپذیر). یک «مسیر قابل‌ممیزی از سؤال تا ارزیابی نهایی روی داده‌ی کنار گذاشته‌شده». این جلسه بخش‌های ۰۱، ۰۲، ۰۳ و ۰۵ را پوشش می‌دهد و بخش ۰۴ (رویداد نادر) مال جلسه‌ی ۸ است.

۲ مورد درس: «آیا این سفر لغو می‌شود؟» و قرارداد لحظه‌ی پیش‌بینی اسلاید امتحانی

مسئله‌ی جلسه‌های قبل «۱۲٪ افت سفرهای تکمیل‌شده» بود. یکی از فرضیه‌ها لغو سفر بود. حالا می‌خواهیم قبل از این‌که لغو اتفاق بیفتد ریسکش را پیش‌بینی کنیم تا مثلاً راننده‌ی نزدیک‌تری بفرستیم یا به مسافر پیام بدهیم. داده‌ی مصنوعی اسلاید: ۹٬۶۰۰ سفر، حدود ۱۲٪ لغوشده، در ۱۸۰ روز.

تعریف ۷.۱ · لحظه‌ی پیش‌بینی (prediction moment)
نقطه‌ای در زمان که مدل در استقرار واقعی باید جواب بدهد. در این مسئله: همان لحظه‌ای که مسافر درخواست سفر می‌دهد، نه بعد از تمام شدن سفر. هر چیزی که بعد از این لحظه به وجود می‌آید، برای مدل «آینده» است.
قانون شماره‌ی ۱ (Rule #1)
در لحظه‌ی پیش‌بینی، آیا این ویژگی از قبل وجود داشت؟ (At prediction time, would this feature already exist?)

اسلاید ۶ این قانون را به یک قرارداد لحظه‌ی پیش‌بینی (prediction-time contract) تبدیل می‌کند: قبل از تقسیم داده دقیقاً تصمیم بگیر مدل اجازه‌ی دیدن چه اطلاعاتی را دارد.

✅ موجود در لحظه‌ی درخواست: ورودی‌های مجاز

  • شهر، زمان درخواست
  • فاصله‌ی تخمینی، قیمت پیشنهادی (price quote)
  • ETA مورد انتظار راننده
  • سابقه‌ی واقعی قبلی کاربر (genuine prior user history)

⛔ فقط بعداً معلوم می‌شود: ورودی‌های ممنوع

  • وضعیت نهایی سفر
  • بازپرداخت انجام‌شده (refund issued)
  • زمان واقعی پیاده شدن (actual drop-off)
  • دلیل لغو (cancellation reason)
  • اصلاحیه‌های بعد از نتیجه (post-outcome corrections)
⚠ نکته‌ی امتحانی: «در دسترس بودن، نه همبستگی»
جمله‌ی پایین اسلاید ۶ را حفظ کن: Availability, not correlation, decides whether a feature is valid. این‌که یک ستون با برچسب همبستگی بالایی دارد، دلیل خوب بودنش نیست. اغلب دقیقاً برعکس: ستونی که «خیلی خوب» پیش‌بینی می‌کند، اول از همه مشکوک به نشت است. معیار فقط این است که آن ستون در لحظه‌ی درخواست وجود داشته یا نه.

برای بقیه‌ی جلسه یک داده‌ی مصنوعی شبیه داده‌ی اسلاید می‌سازیم. هر کاربر یک «عادت لغو» پنهان دارد که مدل مستقیم آن را نمی‌بیند. این همان چیزی است که بعداً باعث نشت هویت می‌شود. کد را در یک نوت‌بوک اجرا کن. بقیه‌ی قطعه‌ها ادامه‌ی همین نوت‌بوک‌اند.

import numpy as np, pandas as pd

def make_rides(n=9600, n_users=400, seed=7):
    """Synthetic ride requests: 180 days, ~12% cancelled, repeated users."""
    rng = np.random.default_rng(seed)
    users = pd.DataFrame({
        "user_id": np.arange(n_users),
        "home_city": rng.choice(["Tehran", "Mashhad", "Isfahan", "Shiraz", "Tabriz"],
                                n_users, p=[.45, .2, .13, .12, .1]),
        "flaky": rng.normal(0, 1.4, n_users),          # hidden habit: NOT a column we may use
        "signup_days": rng.integers(30, 2000, n_users)})
    uid = rng.integers(0, n_users, n)
    t0 = pd.Timestamp("2026-01-01")
    req = (t0 + pd.to_timedelta(rng.uniform(0, 180*24*3600, n), unit="s")).floor("min")
    df = pd.DataFrame({"user_id": uid, "request_time": req}).merge(users, on="user_id")
    df = df.rename(columns={"home_city": "city"})
    df["hour"] = df.request_time.dt.hour
    df["distance_km"] = np.round(rng.gamma(2.2, 3.0, n), 1)
    df["eta_min"] = np.clip(np.round(rng.gamma(3, 2.5, n) + (df.city == "Tehran")*3), 1, 40)
    df["fare"] = (np.round((25000 + 9000*df.distance_km) * rng.uniform(.9, 1.3, n), -3)).astype(int)
    z = (-2.9 + 0.12*(df.eta_min - 8) + 1.0*df.flaky
         + 0.35*df.hour.isin([7, 8, 17, 18, 19]) + 0.03*df.distance_km)
    df["cancelled"] = (rng.uniform(size=n) < 1/(1 + np.exp(-z))).astype(int)
    # refund is CREATED BY the cancellation -> a post-outcome column
    df["refund_issued"] = np.where(df.cancelled == 1, rng.uniform(size=n) < .93,
                                   rng.uniform(size=n) < .01).astype(int)
    return df.drop(columns="flaky").sort_values("request_time").reset_index(drop=True)

rides = make_rides()
print(rides.shape, f"cancel rate = {rides.cancelled.mean():.3f}")

۳ تقسیم داده یعنی شبیه‌سازی استقرار اسلاید

اسلاید ۸ می‌گوید: «تصادفی بودن هدف نیست. تعمیم به آینده هدف است.» تقسیم train/test یک «تمرین لباس‌پوشیده» برای روز استقرار است. پس اول باید بپرسی مدل به چه کسی، کجا و کی سرویس می‌دهد. سه سؤال اسلاید سه طراحی متفاوت می‌خواهند:

سؤال A · سفر بعدیمی‌توانی روی سفرهای قبلی آموزش بدهی، ولی باید روی درخواست‌های بعدی تست کنی. ← تقسیم زمانی.
سؤال B · کاربر جدیدکاربری که هم در train است و هم در test یک میان‌بُر است، نه تعمیم به کاربر جدید. ← تقسیم گروهی.
سؤال C · شهر جدیدارزیابی با کنار گذاشتن یک شهر (city-held-out) انتقال جغرافیایی را می‌سنجد. ← یک شهر کامل در test.
اصل طراحی
The correct split depends on whom, where and when the model will serve. تقسیم درست به این بستگی دارد که مدل به چه کسی، کجا و کی سرویس می‌دهد.

۳.۱ train، validation، test: سه کار متفاوت

بخشکارشچه چیزی روی آن fit می‌شودچند بار نگاهش می‌کنی
Train (ژانویه تا آوریل)یادگرفتن پارامترهای مدل و پیش‌پردازش (میانه‌ی imputer، میانگین scaler، دسته‌های encoder)همه‌چیزهر چند بار که بخواهی
Validation (مه)انتخاب مدل، ابرپارامتر، آستانههیچ‌چیز (فقط امتیاز می‌گیرد)زیاد، و به همین دلیل کم‌کم «خوش‌بین» می‌شود
Test (ژوئن)یک ممیزی نهایی و گزارشهیچ‌چیزیک بار
⚠ نکته‌ی امتحانی: مجموعه‌ی test یک صندوق قفل‌شده است
اگر با دیدن امتیاز test چیزی را تغییر بدهی (ویژگی، آستانه، مدل)، آن مجموعه دیگر test نیست، validation شده است. عددی که روی آن گزارش می‌دهی دیگر تخمین بی‌طرفی از آینده نیست. سؤال رایج امتحان: «تیم ۷ بار روی test آستانه را عوض کرد. مشکل چیست؟» جواب: test به validation تبدیل شده و برای تخمین بی‌طرف یک دوره‌ی تازه (مثلاً ژوئیه) لازم است.

۳.۲ لایه‌بندی (stratification) کی کمک می‌کند؟

با ۱۲٪ لغو، یک تقسیم تصادفی ساده ممکن است سهم لغوها را در train، val و test نابرابر کند. تقسیم لایه‌ای نسبت کلاس‌ها را در هر بخش ثابت نگه می‌دارد. اسلاید ۱۰ این را با سه نوار نشان می‌دهد: در تقسیم ساده، تکه‌ی نارنجی (cancelled) در val بزرگ‌تر از بقیه است. در تقسیم لایه‌ای هر سه یکسان‌اند. زیرعنوان اسلاید هم مهم است: «یک پیش‌فرض مفید برای طبقه‌بندی IID، نه جایگزینی برای اعتبار زمانی».

چقدر نابرابری؟ اگر test فقط $m$ سطر داشته باشد و نرخ لغو $\pi$ باشد، تعداد لغوهای test تقریباً دوجمله‌ای است با انحراف معیار $\sqrt{m\pi(1-\pi)}$. برای یک پایلوت ۵۰۰‌سفره در تبریز با test صدتایی: $\sqrt{100\times0.12\times0.88}\approx3.25$. یعنی «۱۲ لغو» به‌راحتی ۶ یا ۱۸ می‌شود. شبیه‌سازی:

from sklearn.model_selection import train_test_split
y = np.r_[np.ones(60), np.zeros(440)].astype(int)          # 500 rides, 12% cancelled
rnd   = [train_test_split(y, test_size=100, random_state=s)[1].sum() for s in range(1000)]
strat = [train_test_split(y, test_size=100, stratify=y, random_state=s)[1].sum() for s in range(1000)]
print(f"random    : cancelled in test  min={min(rnd)}  max={max(rnd)}  std={np.std(rnd):.2f}")
print(f"stratified: cancelled in test  min={min(strat)}  max={max(strat)}  std={np.std(strat):.2f}")

انحراف معیار شبیه‌سازی (۲٫۸۶) کمی کمتر از ۳٫۲۵ است، چون نمونه‌گیری بدون جای‌گذاری از جمعیت محدود است (توزیع فوق‌هندسی). در بدترین قرعه فقط ۳ لغو در test هست. با ۳ نمونه‌ی مثبت هیچ recall یا PR-AUC معناداری نمی‌شود حساب کرد.

❌ اشتباه رایج: «stratify زدم، پس تقسیمم درست است»
stratification فقط نسبت کلاس را درست می‌کند. اگر سفرهای ژوئن در train باشند و سفرهای مارس در test، یا یک کاربر در هر دو طرف باشد، stratify=y هیچ‌کدام را درست نمی‌کند. اول سؤال استقرار (زمان؟ کاربر؟ شهر؟) را جواب بده، بعد اگر لازم بود لایه‌بندی را اضافه کن (مثلاً StratifiedGroupKFold).

from sklearn.ensemble import RandomForestClassifier
from sklearn.model_selection import KFold, GroupKFold, cross_val_score

X = rides[["hour", "distance_km", "eta_min", "fare", "signup_days"]]
y = rides.cancelled
rf = RandomForestClassifier(n_estimators=300, min_samples_leaf=3, n_jobs=-1, random_state=0)
for name, cv, g in [("KFold (row-wise)", KFold(5, shuffle=True, random_state=0), None),
                    ("GroupKFold(user)", GroupKFold(5), rides.user_id)]:
    s = cross_val_score(rf, X, y, cv=cv, groups=g, scoring="roc_auc")
    print(f"{name:18s} AUC = {s.mean():.3f} ± {s.std():.3f}")

# leakage check you should always run:
tr, va = next(KFold(5, shuffle=True, random_state=0).split(X))
shared = set(rides.user_id.iloc[tr]) & set(rides.user_id.iloc[va])

۴.۲ اعتبارسنجی زمانی به شکاف (gap) نیاز دارد

چرا شکاف؟ فرض کن برچسب لغو تا ۲۴ ساعت بعد از درخواست قطعی می‌شود (مثلاً لغو دیرهنگام یا اصلاح وضعیت). روزی که مدل را آموزش می‌دهی و مستقر می‌کنی، برچسب سفرهای ۲۴ ساعت آخر هنوز معلوم نیست. اگر در شبیه‌سازی، train درست تا لحظه‌ی شروع validation ادامه پیدا کند، از برچسب‌هایی استفاده کرده‌ای که در واقعیت نداشتی. اسلاید سه نکته دارد:

  • مثال: برچسب لغو تا ۲۴ ساعت بعد از درخواست نهایی می‌شود.
  • اگر برچسب‌ها با مرز ارزیابی هم‌پوشانی دارند، یک embargo / gap تعریف کن.
  • TimeSeriesSplit گزینه‌ی gap دارد، ولی فرض‌هایش باید بررسی شود.

یکی از آن فرض‌ها این است: gap بر حسب تعداد سطر است، نه ساعت. TimeSeriesSplit فرض می‌کند سطرها به ترتیب زمانی‌اند و فاصله‌ی زمانی بین‌شان کمابیش یکسان است. با حدود ۵۳ سفر در روز، gap=55 تقریباً یک روز است:

from sklearn.model_selection import TimeSeriesSplit
print("rides per day ≈", round(len(rides) / 180, 1))
tss = TimeSeriesSplit(n_splits=4, gap=55)     # gap counts ROWS (~1 day), not hours!
for i, (tr, va) in enumerate(tss.split(rides)):   # rides must be sorted by request_time
    t = rides.request_time
    print(f"fold {i+1}: train ..{t[tr[-1]]:%m-%d %H:%M}  |gap|  val {t[va[0]]:%m-%d %H:%M}..{t[va[-1]]:%m-%d}"
          f"  (n_train={len(tr)}, n_val={len(va)})")

شکاف واقعی بین ۲۴٫۵ تا ۲۷ ساعت است، نه دقیقاً ۲۴. اگر تعداد سفر در روز خیلی نوسان دارد (تعطیلات، شب‌ها)، به‌جای gap سطری، مرزها را مستقیم با تاریخ بساز: train = rides[t < cut - 1 day] و val = rides[(t >= cut) & (t < cut + 30 days)]. پنجره‌ی train هم در TimeSeriesSplit گسترش‌یابنده (expanding) است. اگر رفتار کاربران خیلی عوض می‌شود، max_train_size پنجره را لغزان (rolling) می‌کند.

۴.۳ splitter را با ریسک انتخاب کن

اسلاید ۱۳: قبل از انتخاب splitter یک سؤال مشخص بپرس.

جدول کامل‌تر، با «کی استفاده کن» و «ریسک»: تکمیلی

TimeSeriesSplit(gap=g)گذشته قبل از آینده. سطرها مرتب و با فاصله‌ی کمابیش یکسانپیش‌بینی درخواست‌های آیندهgap سطری است نه زمانی. foldهای اول train کوچکی دارند. کاربر می‌تواند در دو طرف باشد (که برای سؤال A اشکالی ندارد)

💡 ترکیب کردن مجاز است
سؤال «کاربر جدید در ماه آینده» هم زمان و هم گروه را می‌خواهد: اول دوره‌ی test را از نظر زمانی جدا کن (ژوئن)، بعد از test فقط کاربرانی را نگه دار که قبل از ژوئن هیچ سفری نداشته‌اند. scikit-learn برای این ترکیب splitter آماده ندارد. با چند خط pandas می‌سازی و ایندکس‌ها را به cv= می‌دهی (لیستی از (train_idx, val_idx)).

با ویجت زیر خودت ببین هر splitter چه سطرهایی را کجا می‌فرستد. ده کاربر، هر نقطه یک سفر، مربع یعنی سفر لغوشده.

با ویجت این کارها را بکن
(۱) روی «تصادفی» چند بار «قرعه‌ی دوباره» بزن و درصد لغو test را نگاه کن، بعد «لایه‌ای» را امتحان کن. (۲) «گروهی» را بزن: نشت هویت صفر می‌شود، ولی نشت آینده نه. (۳) «زمانی» را با شکاف ۰ و تأخیر برچسب ۱ روز ببین: هشدار نشت برچسب می‌آید. شکاف را به ۱ روز برسان تا رفع شود. (۴) شکاف خیلی بزرگ هم هزینه دارد: سفرهای خاکستری دور ریخته می‌شوند.

۵ اعتبارسنجی متقاطع: تمرین‌های صادقانه‌ی متعدد اسلاید

یک تقسیم train/validation یک «تمرین» است. اعتبارسنجی متقاطع (cross-validation) همین تمرین را چند بار تکرار می‌کند: هر سطر جدول یک تقسیم تازه است. مدل روی بخش آبی fit و روی بخش سبز امتیازدهی می‌شود. هر سطر داده دقیقاً یک بار در validation حضور دارد.

۵.۲ انتخاب مدل بیرون از مجموعه‌ی test زندگی می‌کند

اسلاید ۱۶: «امتیاز test یک تخمین نهایی است، نه یک ابزار طراحی». داده به سه منطقه تقسیم می‌شود:

⚠ نکته‌ی امتحانی
«If you repeatedly inspect test scores to choose settings, you are training on the test.» اگر بارها امتیاز test را نگاه کنی تا تنظیمات را انتخاب کنی، داری روی test آموزش می‌دهی، فقط با یک واسطه‌ی انسانی.

۵.۳ چرا بهترین امتیاز grid search خوش‌بینانه است؟ CV تودرتو تکمیلی

وقتی ۴۰ تنظیم ابرپارامتر را با CV امتحان می‌کنی و بیشینه را گزارش می‌کنی، آن بیشینه دو چیز را با هم دارد: کیفیت واقعی بهترین تنظیم، به‌اضافه‌ی شانس. هر امتیاز CV یک تخمین نویزی است. ماکزیمم ۴۰ تخمین نویزی به‌طور سیستماتیک از مقدار واقعی بالاتر است. اسمش «نفرین برنده» (winner's curse) یا سوگیری انتخاب است:

$$\mathbb{E}\Big[\max_{j}\hat s_j\Big]\;\ge\;\max_j\,\mathbb{E}[\hat s_j].$$

CV تودرتو (nested CV) راه‌حل است: یک حلقه‌ی درونی ابرپارامتر را انتخاب می‌کند و یک حلقه‌ی بیرونی کل فرایند «تنظیم + آموزش» را روی داده‌ای ارزیابی می‌کند که تنظیم آن را ندیده. در sklearn کافی است خود GridSearchCV را به‌عنوان estimator به cross_val_score بدهی. روی ۱۰ دیتاست نویز خالص (دقت واقعی = ۰٫۵۰):

from sklearn.neighbors import KNeighborsClassifier
from sklearn.model_selection import GridSearchCV, StratifiedKFold, cross_val_score

grid = {"n_neighbors": list(range(1, 40, 2)), "weights": ["uniform", "distance"]}  # 40 settings
flat, nested = [], []
for seed in range(10):                                   # 10 pure-noise datasets
    rng = np.random.default_rng(seed)
    X, y = rng.normal(size=(150, 10)), rng.integers(0, 2, 150)   # true accuracy = 0.50
    inner = StratifiedKFold(5, shuffle=True, random_state=1)
    outer = StratifiedKFold(5, shuffle=True, random_state=2)
    gs = GridSearchCV(KNeighborsClassifier(), grid, cv=inner)
    flat.append(gs.fit(X, y).best_score_)                       # tune & report on same folds
    nested.append(cross_val_score(gs, X, y, cv=outer).mean())   # tuning repeated inside each outer fold
print(f"non-nested best_score_ : {np.mean(flat):.3f}")
print(f"nested CV estimate     : {np.mean(nested):.3f}")
non-nested best_score_ : 0.568 nested CV estimate : 0.515

روی دیتاست‌های تکی ممکن است ترتیب برعکس شود (نویز است)، ولی به‌طور میانگین best_score_ حدود ۵ واحد درصد خوش‌بین است و تخمین تودرتو به ۰٫۵ نزدیک است. هزینه‌اش: $5\times(40\times5+1)=1005$ بار fit. در داده‌ی زمانی معمولاً به‌جای nested CV همان ساختار اسلاید ۱۶ کافی است: CV روی دوره‌ی development و یک دوره‌ی validation جدا.

۵.۴ عدم‌قطعیت عملکرد را گزارش کن

اسلاید ۱۷: «یک fold خوش‌شانس سیستم قوی را ثابت نمی‌کند.» عددهای اسلاید (Average Precision در ۵ fold):

گزارش میانگین ± انحراف معیار تکمیلی
برای $K$ امتیاز fold یعنی $s_1,\dots,s_K$: $$\bar s=\frac1K\sum_{k=1}^K s_k,\qquad \mathrm{sd}=\sqrt{\frac{1}{K-1}\sum_{k=1}^K (s_k-\bar s)^2},\qquad \mathrm{SE}\approx\frac{\mathrm{sd}}{\sqrt K}.$$ عددهای اسلاید: $\bar s=1.63/5=0.326$، $\mathrm{sd}\approx0.071$ و $\mathrm{SE}\approx0.032$. گزارش درست: «AP = ۰٫۳۳ ± ۰٫۰۷ (انحراف معیار بین ۵ fold، بازه‌ی ۰٫۲۵ تا ۰٫۴۳)» به‌اضافه‌ی جدول هر fold.
احتیاط: foldهای CV مستقل نیستند (trainهایشان هم‌پوشانی دارد)، پس $\mathrm{SE}$ بالا عدم‌قطعیت را کمتر از واقع نشان می‌دهد. sd بین foldها را به‌عنوان «پراکندگی» گزارش کن، نه یک بازه‌ی اطمینان دقیق.

چرا یک تقسیم تکی کافی نیست؟ همان مدل ساده (چهار ویژگی لحظه‌ی درخواست) را با ۳۰ تقسیم تصادفی ۸۰/۲۰ ارزیابی کردیم. فقط random_state فرق داشت:

from sklearn.pipeline import make_pipeline
from sklearn.impute import SimpleImputer
from sklearn.preprocessing import StandardScaler
from sklearn.linear_model import LogisticRegression
from sklearn.metrics import average_precision_score

cols = ["eta_min", "distance_km", "fare", "hour"]
aps = []
for seed in range(30):
    Xtr, Xte, ytr, yte = train_test_split(rides[cols], rides.cancelled, test_size=0.2,
                                          stratify=rides.cancelled, random_state=seed)
    m = make_pipeline(SimpleImputer(strategy="median"), StandardScaler(),
                      LogisticRegression(max_iter=1000)).fit(Xtr, ytr)
    aps.append(average_precision_score(yte, m.predict_proba(Xte)[:, 1]))
aps = np.array(aps)
print(f"30 random 80/20 splits: AP min={aps.min():.3f}  max={aps.max():.3f}  "
      f"mean={aps.mean():.3f}  std={aps.std(ddof=1):.3f}")
30 random 80/20 splits: AP min=0.161 max=0.265 mean=0.217 std=0.022

یک مدل، یک داده، و AP از ۰٫۱۶ تا ۰٫۲۷ فقط با عوض کردن seed. اگر دو مدل را هر کدام با یک تقسیم تکی مقایسه کنی، فرق ۰٫۰۳ ممکن است کاملاً تصادفی باشد. برای مقایسه‌ی دو مدل، آن‌ها را روی همان foldها اجرا کن و تفاوت جفتی را در هر fold ببین (تمرین ۳). این تمرین فقط برای نشان دادن نویز است. برای مسئله‌ی لغو، تقسیم درست همان تقسیم زمانی است.

۶ نشت: سه مسیر به اطمینان کاذب اسلاید امتحانی

اسلاید ۱۸: «یک امتیاز بالا می‌تواند یک باگ نرم‌افزاری در لباس مبدل باشد.» نشت داده (data leakage) یعنی در آموزش یا ارزیابی، اطلاعاتی به مدل برسد که در لحظه‌ی پیش‌بینی واقعی در دسترس نیست. نتیجه‌اش امتیازی است که در استقرار تکرار نمی‌شود. اسلاید سه مسیر را نام می‌برد:

۱. پس از نتیجه · سفر در زمان (Time travel)refund issued، نتیجه‌ی نهایی، یا ستونی که فقط بعد از لغو پر می‌شود.
۲. میان‌بُر هویت · حفظ کردن (Memorization)همان کاربر، رویداد تکراری، یا نماینده‌های شناسایی‌کننده‌ی قوی که بین splitها نشت می‌کنند.
۳. پیش‌پردازش · fit سراسری (Global fitting)imputation، PCA، encoding، انتخاب ویژگی یا نمونه‌گیری مجدد که قبل از CV روی کل داده fit شده‌اند.
جمع‌بندی اسلاید
False confidence can come from feature values, row relations, or the workflow. اطمینان کاذب از مقدار ویژگی‌ها، از رابطه‌ی بین سطرها، یا از روند کار می‌آید.

۶.۳ target encoding فقط out-of-fold تکمیلی

دو ظرافت داریم: (۱) فقط سفرهایی که برچسبشان قبل از درخواست فعلی نهایی شده حساب شوند. برچسب ۲۴ ساعت بعد نهایی می‌شود، پس «زمان دانستن» هر برچسب request_time + 24h است.     "ride_id": [1, 2, 3, 4, 5, 6, 7],
    "user_id": [12, 12, 12, 12, 47, 47, 47],
    "request_time": pd.to_datetime(["2026-01-04 08:00", "2026-01-04 20:00", "2026-01-10 09:00",
                                    "2026-01-17 18:00", "2026-01-05 07:30", "2026-01-06 07:30",
                                    "2026-01-09 08:00"]),
    "cancelled": [1, 0, 0, 1, 1, 0, 0]})
LABEL_DELAY = pd.Timedelta("24h")            # label is final 24h after request

def add_past_cancel_rate(df):
    hist = df[["user_id", "request_time", "cancelled"]].copy()
    hist["label_time"] = hist.request_time + LABEL_DELAY     # when the label becomes KNOWN
    hist = hist.sort_values("label_time")
    g = hist.groupby("user_id")
    hist["n_known"] = g.cumcount() + 1                       # labels known up to this label_time
    hist["n_cancel_known"] = g.cancelled.cumsum()
    out = pd.merge_asof(
        df.sort_values("request_time"),
        hist[["user_id", "label_time", "n_known", "n_cancel_known"]],
        left_on="request_time", right_on="label_time", by="user_id",
        direction="backward", allow_exact_matches=False)   # strictly BEFORE the request
    out[["n_known", "n_cancel_known"]] = out[["n_known", "n_cancel_known"]].fillna(0).astype(int)
    out["past_cancel_rate"] = out.n_cancel_known / out.n_known.replace(0, np.nan)
    return out.drop(columns="label_time")

در دنیای واقعی: feature store و جدول‌های «as of»
در شرکت‌های بزرگ، همین مسئله را «point-in-time join» می‌نامند و feature storeها (مثل Feast) آن را خودکار انجام می‌دهند. ولی منطق همین است: هر مقدار ویژگی یک زمان اعتبار دارد و join باید با «آخرین مقدار معتبر قبل از لحظه‌ی پیش‌بینی» انجام شود. اگر جدولی فقط مقدار فعلی را نگه می‌دارد (بدون تاریخچه)، نمی‌توانی از آن ویژگی point-in-time بسازی.

۸ تجسس در داده و چک‌لیست تیم قرمز اسلاید امتحانی

اسلاید ۲۰: «تجسس در داده (data snooping) می‌تواند از نویز سیگنال بسازد.» انتخاب «بهترین» ویژگی‌ها روی کل داده، validation را آلوده می‌کند.

❌ WRONG

  1. ویژگی‌ها را با همه‌ی سطرها انتخاب کن
  2. مدل را cross-validate کن
  3. امتیاز خوش‌بینانه گزارش کن

✅ RIGHT

  1. داده را به foldهای CV تقسیم کن
  2. انتخاب ویژگی را داخل train fold fit کن
  3. فقط روی validation دست‌نخورده امتیاز بگیر
پیام پایین اسلاید
Even “unsupervised” transformations should be fit on training data only. حتی تبدیل‌های «بدون ناظر» (مثل PCA، scaler، imputer) هم فقط باید روی داده‌ی train fit شوند.

چرا از نویز سیگنال ساخته می‌شود؟ با $n$ نمونه و $p$ ویژگی نویز، همبستگی هر ویژگی با برچسب تصادفی تقریباً $\mathcal N(0,1/n)$ است. بزرگ‌ترین همبستگی از بین $p$ تا حدوداً $\sqrt{2\ln p/n}$ است. با $n=100$ و $p=5000$ می‌شود $\sqrt{2\times8.52/100}\approx0.41$. اگر ۲۰ ویژگی برتر را روی کل داده انتخاب کنی، ویژگی‌هایی را برداشته‌ای که اتفاقاً روی همین ۱۰۰ سطر (از جمله سطرهایی که بعداً validation می‌شوند) با برچسب هم‌خوان‌اند. این آزمایش کلاسیک را خودمان اجرا کردیم:

from sklearn.feature_selection import SelectKBest, f_classif

rng = np.random.default_rng(0)
n, p, k = 100, 5000, 20
X = rng.normal(size=(n, p))          # pure noise
y = rng.integers(0, 2, size=n)       # random labels -> true accuracy is 50%
cv = StratifiedKFold(5, shuffle=True, random_state=0)

# WRONG: select on all rows, then CV
X_sel = SelectKBest(f_classif, k=k).fit_transform(X, y)
wrong = cross_val_score(LogisticRegression(max_iter=1000), X_sel, y, cv=cv)

# RIGHT: selection inside the pipeline (refit in every training fold)
pipe = make_pipeline(SelectKBest(f_classif, k=k), LogisticRegression(max_iter=1000))
right = cross_val_score(pipe, X, y, cv=cv)
print(f"WRONG (select outside CV): {wrong.mean():.3f} ± {wrong.std():.3f}")
print(f"RIGHT (select inside CV):  {right.mean():.3f} ± {right.std():.3f}")

⚠ نکته‌ی امتحانی: این همان اشتباه معروف ESL است
در کتاب Elements of Statistical Learning (بخش ۷.۱۰.۲، «The Wrong and Right Way to Do Cross-validation») همین سناریو آمده است. قاعده: هر مرحله‌ای که به برچسب‌ها نگاه می‌کند (انتخاب ویژگی، target encoding، تنظیم آستانه، oversampling) باید داخل حلقه‌ی CV تکرار شود. مراحل بدون ناظر معمولاً نشت کوچک‌تری دارند، ولی قاعده‌ی اسلاید برای آن‌ها هم همین است.

۸.۱ شش سؤال در بازبینی تیم قرمز نشت

اسلاید ۲۱: «این چک‌لیست را قبل از باور کردن امتیاز cross-validation یک مدل اجرا کن.» «تیم قرمز» یعنی کسی که نقش مهاجم را بازی می‌کند و تلاش می‌کند ثابت کند عدد تو دروغ است.

۹ pipeline داخل هر fold دوباره fit می‌شود اسلاید

اسلاید ۲۲: «مرز fit / transform از انتخاب estimator مهم‌تر است.» در هر fold:

TRAIN FOLD←FIT IMPUTER←FIT ENCODER←FIT SCALER←FIT MODEL
VALIDATION FOLD←transform←predict←score(هرگز fit نمی‌شود)

«Cross-validation clones and re-fits the full pipeline in every split.» cross_val_score در هر split یک کپی تازه (clone) از کل pipeline می‌سازد و همه‌ی مراحل را فقط روی train همان split، fit می‌کند. به همین دلیل اگر چیزی بیرون از pipeline fit شود، CV نمی‌تواند از آن محافظت کند.

۹.۱ پایتون زنده: حداقل pipeline قابل‌اعتماد

اسلاید ۲۳ (عین کد اسلاید): «هر چیزی که از داده یاد می‌گیرد باید داخل estimator باشد.»

                ('scale', StandardScaler())])
cat = Pipeline([('fill', SimpleImputer(strategy='most_frequent')),
                ('ohe', OneHotEncoder(handle_unknown='ignore'))])
prep = ColumnTransformer([('num', num, numeric_cols),

model = Pipeline([('prep', prep),
                  ('clf', LogisticRegression(max_iter=1000))])

hist["cum_cancel"] = hist.groupby("user_id").cancelled.cumsum()
h = hist[["user_id", "label_time", "cum_cancel"]]

def cum_as_of(df, when):                       # cancellations KNOWN strictly before `when`
    q = df[["user_id"]].assign(t=when).sort_values("t")
    m = pd.merge_asof(q, h, left_on="t", right_on="label_time", by="user_id",
                      direction="backward", allow_exact_matches=False)
    m.index = q.index                          # merge_asof resets the index
    return m.cum_cancel.fillna(0).reindex(df.index)

در بخش ۴.۱ دیدیم KFold عدد ۰٫۶۴۰ و GroupKFold عدد ۰٫۵۹۸ داد. هم‌تیمی‌ات می‌گوید: «مدل ما برای کاربران فعلی در ماه آینده است، پس شناختن کاربر اشکالی ندارد و ۰٫۶۴ درست است.» تا کجا حق دارد و کجا اشتباه می‌کند؟ چه آزمایشی اختلاف را حل می‌کند؟
راه‌حلحق دارد که برای کاربران فعلی، استفاده از اطلاعات کاربر مجاز است و GroupKFold (که کاربران را کاملاً نادیده نگه می‌دارد) برای این سؤال بیش از حد بدبینانه است. اشتباهش این است که KFold تصادفی به مدل اجازه می‌دهد عادت کاربر را از سفرهای آینده‌ی او یاد بگیرد (سفر ژوئن در train، سفر مارس در val). در استقرار، فقط گذشته‌ی کاربر را داری. پس ۰٫۶۴ هم نشت زمانی دارد. علاوه بر این، signup_days یک شناسه‌ی پنهان است و مدل از طریق آن «حفظ» می‌کند، نه از طریق یک ویژگی معنادار. آزمایش درست: split زمانی (train تا آوریل، test ژوئن) + ویژگی صریح past_cancel_rate به‌شکل point-in-time. این همان چیزی است که در بخش ۷ AP را از ۰٫۲۲ به ۰٫۴۲ رساند، به‌روشی که در استقرار هم تکرار می‌شود. و اگر بخشی از کاربران ژوئیه تازه‌وارد باشند، نتیجه را برای این دو slice جدا گزارش کن.
تمرین ۸· 🔴 تحلیلی
در آزمایش تجسس ($n=100$، $p=5000$، $k=20$) نسخه‌ی غلط ۸۷٪ داد. (الف) با تقریب $\sqrt{2\ln p/n}$ بزرگ‌ترین همبستگی تصادفی را تخمین بزن. (ب) پیش‌بینی کن اگر $n$ را به ۱۰۰۰ برسانی یا $p$ را به ۵۰ کم کنی، فاصله‌ی «غلط» و «درست» چه تغییری می‌کند. با ویجت بخش ۸ چک کن. (ج) چرا نسخه‌ی درست دقیقاً ۵۰٪ نیست و sd آن (۰٫۰۹۵) از نسخه‌ی غلط بیشتر است؟
راه‌حل(الف) $\sqrt{2\ln5000/100}=\sqrt{17.03/100}\approx0.41$. (در شبیه‌سازی ما بزرگ‌ترین همبستگی ۰٫۳۵ بود و ۲۰ تای برتر بالای ۰٫۲۸ بودند. این تقریب یک کران بالای خوب است.) (ب) همبستگی جعلی با $1/\sqrt n$ کوچک می‌شود و فقط با $\sqrt{\ln p}$ بزرگ می‌شود. با $n$ بزرگ‌تر، ویژگی‌های انتخاب‌شده سیگنال جعلی کمتری دارند و فاصله کم می‌شود. با $p$ کوچک، انتخاب «از میان» گزینه‌های کمتری انجام می‌شود و خوش‌بینی کم می‌شود. بدترین حالت $p\gg n$ است، یعنی دقیقاً وضعیت ژنومیک یا متن با هزاران ویژگی. (ج) هر fold فقط ۲۰ نمونه‌ی validation دارد. دقت روی ۲۰ نمونه گسسته است (گام‌های ۵٪) و حول ۵۰٪ با sd حدود $\sqrt{0.25/20}\approx0.11$ نوسان می‌کند. نسخه‌ی غلط sd کمتری دارد چون همه‌ی foldها از یک مجموعه‌ی ویژگی جعلی استفاده می‌کنند که روی همه‌ی سطرها «کار می‌کند». این ثبات خودش یک علامت هشدار است.
تمرین ۹· 🔵 پژوهشگر
شرکت می‌خواهد سرویس را در شهر جدید (رشت) راه بیندازد و فقط داده‌ی پنج شهر فعلی را دارد. یک پروتکل ارزیابی کامل طراحی کن که هم «شهر نادیده» را بسنجد و هم «آینده» را. بگو چه چیزی گزارش می‌کنی و ریسک‌های باقی‌مانده چیست.
راه‌حل (نمونه)(۱) بیرونی: LeaveOneGroupOut با گروه = شهر. هر بار یک شهر کامل test است. (۲) زمان: در هر چرخش، train = چهار شهر دیگر در ژانویه تا آوریل، test = شهر کنار گذاشته‌شده در مه و ژوئن (با شکاف). این «شهر جدید و آینده» را با هم شبیه‌سازی می‌کند. (۳) ویژگی‌ها: ویژگی‌هایی که به شهر وابسته‌اند (one-hot شهر، target encoding منطقه) برای شهر جدید بی‌معنی‌اند. آن‌ها را با ویژگی‌های قابل‌انتقال (تراکم، ETA، ساعت) جایگزین کن. past_cancel_rate برای همه‌ی کاربران رشت در ابتدا NaN است، پس مسیر «کاربر بی‌سابقه» باید جداگانه ارزیابی شود. (۴) گزارش: AP هر شهر جدا، با تعداد لغو و بازه‌ی زمانی. بدترین شهر را برجسته کن، نه فقط میانگین. (۵) ریسک‌ها: فقط ۵ نقطه‌ی «شهر» داری، پس تخمین واریانس انتقال خیلی نامطمئن است. رشت ممکن است از همه‌ی پنج شهر متفاوت باشد (آب‌وهوا، الگوی ترافیک). پیشنهاد: استقرار مرحله‌ای (shadow mode) و پایش AP روی برچسب‌های واقعی رشت در هفته‌های اول.
تمرین ۱۰· 🔵 پژوهشگر
(الف) هزینه‌ی nested CV با grid ۴۰تایی، CV درونی ۵‌تایی و CV بیرونی ۵‌تایی، بر حسب تعداد fit، چقدر است (refit بعد از هر جست‌وجو را هم بشمار)؟ (ب) چه زمانی می‌توانی به‌جای nested CV از «CV روی development + یک دوره‌ی validation جدا» (اسلاید ۱۶) استفاده کنی؟ (ج) آیا nested CV مسئله‌ی «انتخاب ویژگی خارج از fold» را هم حل می‌کند؟
راه‌حل(الف) هر fold بیرونی: $40\times5=200$ fit درونی + ۱ refit بهترین تنظیم روی کل train بیرونی، یعنی ۲۰۱. ضرب در ۵ fold بیرونی: ۱۰۰۵ fit. اگر مدل نهایی را هم با یک grid search روی کل داده بسازی، ۲۰۱ fit دیگر اضافه می‌شود. (ب) وقتی داده کافی است تا یک دوره‌ی validation بزرگ (با تعداد مثبت کافی، مثلاً صدها لغو) کنار بگذاری، و مخصوصاً در داده‌ی زمانی که تقسیم طبیعی زمانی داری. nested CV بیشتر برای داده‌ی کوچک IID ارزش دارد که نمی‌شود چیزی کنار گذاشت. (ج) فقط اگر انتخاب ویژگی داخل pipelineای باشد که در حلقه‌ی درونی fit می‌شود. اگر قبل از همه‌چیز روی کل داده انتخاب کنی، nested CV هم همان ۸۷٪ دروغین را تأیید می‌کند. nested CV فقط از چیزهایی محافظت می‌کند که داخل آن هستند.

۱۳ جمع‌بندی و اصطلاح‌نامه

۵ چیزی که باید یادت بماند

  1. اول لحظه‌ی پیش‌بینی، بعد داده. قبل از split، قرارداد بنویس: چه چیزی در لحظه‌ی درخواست وجود دارد. در دسترس بودن تعیین‌کننده است، نه همبستگی.
  2. split یعنی شبیه‌سازی استقرار. به چه کسی (گروه)، کجا (شهر)، کی (زمان + gap ≥ تأخیر برچسب). stratify فقط نسبت کلاس را درست می‌کند.
  3. test صندوق قفل است. انتخاب مدل در CV و validation، test فقط یک بار. بیشینه‌ی grid search خوش‌بین است (nested CV).
  4. هر چیزی که از داده یاد می‌گیرد داخل pipeline. imputer، scaler، PCA، encoder، انتخاب ویژگی، SMOTE. تجسس روی نویز ۸۷٪ «دقت» ساخت.
  5. عدد تنها گزارش نکن. هر fold با بازه‌ی زمانی و تعداد مثبت، میانگین ± sd، و ویژگی‌های تاریخی فقط point-in-time (merge_asof، allow_exact_matches=False).

اصطلاح‌نامه

prediction moment: لحظه‌ی پیش‌بینی؛ زمانی که مدل در استقرار باید جواب بدهد
prediction-time contract: قرارداد لحظه‌ی پیش‌بینی؛ فهرست ورودی‌های مجاز و ممنوع
data leakage: نشت داده؛ رسیدن اطلاعات غیرقابل‌دسترس در استقرار به آموزش یا ارزیابی
target leakage: نشت هدف؛ ویژگی ساخته‌شده از برچسب یا نتیجه‌ی آن
train-test contamination: آلودگی train و test از طریق پیش‌پردازش یا سطر تکراری
temporal leakage: نشت زمانی؛ استفاده از اطلاعات آینده
holdout / lockbox test: مجموعه‌ی کنار گذاشته‌شده؛ صندوق قفل برای ارزیابی نهایی
validation set: مجموعه‌ی اعتبارسنجی برای انتخاب مدل و آستانه
cross-validation (CV): اعتبارسنجی متقاطع؛ چند تقسیم train/val پشت سر هم
stratification: لایه‌بندی؛ حفظ نسبت کلاس در هر بخش
GroupKFold: تقسیم گروهی؛ هر گروه (کاربر) کامل در یک fold
TimeSeriesSplit / gap / embargo: تقسیم زمانی؛ شکاف بین train و val
nested CV: اعتبارسنجی متقاطع تودرتو برای تنظیم و ارزیابی هم‌زمان
data snooping: تجسس در داده؛ تصمیم‌گیری با دیدن داده‌ی ارزیابی
point-in-time correctness: درستی در لحظه؛ ویژگی فقط از گذشته‌ی هر درخواست
merge_asof: join «آخرین مقدار قبل از لحظه» در pandas
out-of-fold (OOF): مقداری که بدون استفاده از fold خود سطر ساخته شده
Pipeline: زنجیره‌ی پیش‌پردازش و مدل که با هم fit می‌شوند
hyperparameter: ابرپارامتر؛ تنظیمی که از داده یاد گرفته نمی‌شود
average precision (AP): میانگین دقت؛ خلاصه‌ی منحنی precision–recall
