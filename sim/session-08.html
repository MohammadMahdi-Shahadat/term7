پیاده‌سازی: از جاوا تا چارچوب شیءگرا و گراف‌های شبیه‌سازی

تا این‌جا الگوریتم زمان‌بندی رویداد را روی کاغذ اجرا کرده‌ای. حالا همان الگوریتم را سه بار می‌بینی: یک بار به‌صورت یک برنامه‌ی خام جاوا، یک بار به‌صورت یک چارچوب شیءگرا که مدل را از موتور جدا می‌کند، و یک بار به‌صورت گراف — تنها زبان تصویری‌ای که مستقیماً منطق فهرست رویدادهای آینده را مدل می‌کند.

۴. در ابتدای اجرا کدام رویدادها باید در FEL باشند؟ آیا یک قاعده‌ی مکانیکی برای پیدا کردنشان بلدی، یا هر بار شهودی تصمیم می‌گیری؟

01 از جدول دستی به برنامه جزوه

جدول دستی جلسه‌های ۴ تا ۷ دقیقاً همان الگوریتم زمان‌بندی رویداد را اجرا می‌کند، فقط با دست. تا بیست سطر، این بهترین ابزار یادگیری است؛ از هزار مشتری به بالا غیرممکن است. مثال جزوه در این فصل همان فروشگاه است، ولی این بار:

یک سرور، صف FIFOباجه‌ی فروشگاه، صف نامحدود.

این همان سیستم M/M/1 است: ورود پواسون (M)، خدمت نمایی (M) و یک سرور. مزیت بزرگش این است که جواب دقیق نظری دارد، پس می‌شود با آن برنامه را صحت‌سنجی کرد. شدت بار:

$$\rho=\frac{\lambda}{\mu}=\frac{1/4.5}{1/3.2}=\frac{3.2}{4.5}=0.711$$

تعریف ۸.۱ · چهار بخش هر برنامه‌ی زمان‌بندی رویداد
  1. برنامه‌ی اصلی (main): پارامترها را می‌گیرد، مقداردهی اولیه را صدا می‌زند، و حلقه‌ی «رویداد قریب‌الوقوع را بردار ← ساعت را جلو ببر ← روال آن رویداد را صدا بزن» را تا شرط پایان تکرار می‌کند.
  2. مقداردهی اولیه (initialization): ساعت را صفر می‌کند، حالت اولیه‌ی سیستم را می‌سازد، آماره‌های تجمعی را صفر می‌کند و رویداد(های) اولیه را در FEL می‌گذارد.
  3. روال هر رویداد (event routine): برای هر نوع رویداد یکی. سه کار می‌کند: حالت را عوض می‌کند، آماره‌ها را جمع می‌زند، و رویدادهای آینده را زمان‌بندی می‌کند.
  4. گزارش‌گیر (report generator): در پایان، از آماره‌های تجمعی شاخص‌ها را می‌سازد و چاپ می‌کند.
📘 نکته‌ی درسی
در فایل اسلاید، همه‌ی اسلایدهای «Simulation in Java» و چارچوب شیءگرا مُهر OPTIONAL خورده‌اند؛ یعنی جزئیات نحو جاوا موضوع امتحان نیست. آن‌چه می‌ماند این است: کدام آماره کجا جمع می‌شود، چرا lastEventTime لازم است، و چطور همین ساختار را در زبان خودت بنویسی. بخش گراف‌های شبیه‌سازی (بخش ۸ به بعد) مهر OPTIONAL ندارد.

02 متغیرهای شبیه‌سازی و کلاس Event جزوه

قبل از کد، جزوه (ص ۴۱) هر متغیر را در یک دسته می‌گذارد. این دسته‌بندی مهم‌تر از خود کد است، چون در هر مدل تازه باید همین کار را بکنی:

دستهدر این مدلچرا جداست
حالت سیستم (system state)queueLength، numberInServiceهرچه برای ادامه‌ی اجرا لازم است؛ اگر این‌ها را بدانی، گذشته را لازم نداری.
ویژگی موجودیت‌ها (entity attributes)customers (صف مشتری‌ها)داده‌ی هر مشتری، مثل زمان ورودش، که برای محاسبه‌ی زمان در سیستم لازم است.
فهرست رویدادهای آیندهfutureEventListتعهدهای آینده؛ مستقل از حالت فعلی.
مدت فعالیت‌ها (activity durations)meanInterArrivalTime، meanServiceTimeتوزیع‌ها، نه مقدارها. مقدار هر بار تولید می‌شود.
پارامترهای ورودیدو میانگین بالا + totalCustomersچیزی که کاربر عوض می‌کند.
متغیرهای شبیه‌سازیclock، lastEventTime، totalBusy، maxQueueLength، sumResponseTimeانباره‌های تجمعی؛ بخشی از مدل نیستند، ابزار اندازه‌گیری‌اند.
آماره‌های خروجیrho، avgr، pc4فقط در گزارش‌گیر ساخته می‌شوند.
💡 چرا lastEventTime جدا از clock لازم است
بهره‌وری سرور یک انتگرال زمانی است: $\rho=\frac1T\int_0^T B(t)\,dt$ که $B(t)\in\{0,1\}$. چون حالت فقط در لحظه‌ی رویدادها عوض می‌شود، این انتگرال جمعِ طول بازه‌هایی است که $B=1$ بوده. برای شکستن زمان به این بازه‌ها باید «زمان رویداد قبلی» را نگه داری. همین الگو برای میانگین زمانیِ طول صف هم به کار می‌رود (مساحت زیر پلکان $Q(t)$).

کلاس Event (جزوه ص ۴۴)

ساده‌ترین تحقق ممکن یک رویداد: فقط دو ویژگی، نوع و زمان.

class Event {
    public double time;
    private int type;

    public Event(int _type, double _time) {
        type = _type;
        time = _time;
    }

    public int getType()    { return type; }
    public double getTime() { return time; }
}
❌ جایی که این کلاس گول‌زننده است
همین کلاس دو نقش بازی می‌کند. وقتی مشتری وارد می‌شود، خودِ شیء رویداد ورود در صف customers ذخیره می‌شود و بعداً در خروج، finished.getTime() به‌عنوان زمان ورود آن مشتری خوانده می‌شود. یعنی «اعلان رویداد» و «موجودیت مشتری» در این برنامه یکی‌اند. در مدل‌های بزرگ‌تر این کار اشتباه است: مشتری باید کلاس خودش را داشته باشد با ویژگی‌هایش (زمان ورود، نوع، اولویت) و اعلان رویداد فقط به آن اشاره کند.

همان کلاس در پایتون

در پایتون، heapq یک هرم کمینه روی هر شیء مقایسه‌پذیر می‌سازد. پس فقط باید بگوییم رویدادها چطور با هم مقایسه می‌شوند:

import heapq

ARRIVAL, DEPARTURE = 1, 2

class Event:
    __slots__ = ("time", "type", "seq")
    def __init__(self, type_, time, seq=0):
        self.type = type_; self.time = time; self.seq = seq
    def __lt__(self, other):                      # heapq only needs "<"
        return (self.time, self.seq) < (other.time, other.seq)
⚠ نکته‌ی امتحانی · seq چرا لازم است
اگر فقط روی time مقایسه کنی، دو رویدادِ هم‌زمان ترتیب نامعین پیدا می‌کنند و خروجی برنامه با هر اجرا یا هر نسخه‌ی پایتون فرق می‌کند. با افزودن یک شماره‌ی ترتیبیِ صعودی، قاعده‌ی تساوی صریح می‌شود: «هم‌زمان‌ها به ترتیب زمان‌بندی‌شدن». در جلسه‌ی ۷ همین مسئله را با قرارداد «اول خروج، بعد ورود» حل کردی؛ آن‌جا هم باید اولویت را صریح بنویسی، نه این‌که به شانس بسپاری.

03 برنامه‌ی اصلی و مقداردهی اولیه جزوه

public static void main(String argv[]) {
    meanInterArrivalTime = 4.5;
    meanServiceTime      = 3.2;
    totalCustomers       = 1000;
    long seed            = Long.parseLong(argv[0]);

    stream          = new Random(seed);      // Initialize RNG stream
    futureEventList = new EventList();       // Initialize the FEL
    customers       = new Queue();           // Set which holds the customers

    initialization();

    // Loop until first "totalCustomers" have departed
    while (numberOfDepartures < totalCustomers) {
        Event event = (Event) futureEventList.getMin();   // Get imminent event
        futureEventList.dequeue();                        // Be rid of it
        clock = event.getTime();                          // Advance simulation time
        if (event.getType() == ARRIVAL) processArrival(event);
        else                            processDeparture(event);
    }
    reportGeneration();
}

سه خط وسط حلقه، دقیقاً همان «روال پیشروی زمان» جلسه‌ی ۶ است: کم‌ترین زمان را پیدا کن، از فهرست بردار، ساعت را روی آن بگذار. هیچ‌جا ساعت واحدواحد جلو نمی‌رود.

⚠ نکته‌ی امتحانی · شرط پایان
شرط پایان این برنامه شمارشی است: numberOfDepartures < totalCustomers. پس طول اجرا (clock در پایان) خودش یک متغیر تصادفی است، نه عددی ثابت. اگر به‌جایش clock < T می‌گذاشتی، تعداد مشتری تصادفی می‌شد و باید تکلیف مشتریان نیمه‌کاره را هم روشن می‌کردی. این همان تفاوتی است که تمرین ۳ سؤال ۳ می‌پرسد. 
// Seed the event list with TotalCustomers arrivals
public static void initialization() {
    clock = 0.0;
    queueLength = 0;      numberInService = 0;
    lastEventTime = 0.0;  totalBusy = 0;
    maxQueueLength = 0;   sumResponseTime = 0;
    numberOfDepartures = 0;  longService = 0;

    // Create first arrival event
    double eventTime = exponential(stream, meanInterArrivalTime);
    Event event = new Event(ARRIVAL, eventTime);
    futureEventList.enqueue(event);
}
❌ خطای جزوه · توضیح بالای تابع غلط است
کامنت می‌گوید «فهرست رویداد را با TotalCustomers ورود پُر کن»، ولی کد فقط یک ورود می‌سازد. درست همین کد است، نه کامنت: ورودها زنجیره‌ای ساخته می‌شوند، یعنی هر ورود، ورود بعدی را زمان‌بندی می‌کند (بخش ۴). اگر واقعاً هزار ورود را از اول در FEL می‌ریختی، نتیجه از نظر آماری همان بود ولی حافظه و زمان هر insert بی‌دلیل زیاد می‌شد. این دقیقاً همان گره‌ی «یال خودزمان‌بند» در گراف‌های شبیه‌سازی است که در بخش ۹ می‌بینی.
💡 اولین ورود در لحظه‌ی صفر یا بعد از آن؟
این برنامه اولین ورود را در $t=t_A^{(1)}$ می‌گذارد، نه در $t=0$. یعنی سیستم مدتی خالی می‌ماند. در جدول‌های دستی جلسه‌ی ۴ قرارداد برعکس بود (مشتری اول در لحظه‌ی صفر). هیچ‌کدام غلط نیست؛ فقط در گزارشت بنویس کدام را گرفته‌ای، چون روی بهره‌وریِ اجرای کوتاه اثر می‌گذارد. تمرین ۳ سؤال ۸ صریحاً می‌گوید «ورود اول صفر».

04 رویداد ورود و رویداد خروج جزوه امتحانی

public static void processArrival(Event event) {
    customers.enqueue(event);
    queueLength++;

    // If the server is idle, fetch the event, do statistics and put into service
    if (numberInService == 0) scheduleDeparture();
    else totalBusy += (clock - lastEventTime);        // server is busy

    if (maxQueueLength < queueLength) maxQueueLength = queueLength;

    // Schedule the next arrival
    Double eventTime = clock + exponential(stream, meanInterArrivalTime);
    futureEventList.enqueue(new Event(ARRIVAL, eventTime));
    lastEventTime = clock;
}

public static void scheduleDeparture() {
    double serviceTime = exponential(stream, meanServiceTime);
    futureEventList.enqueue(new Event(DEPARTURE, clock + serviceTime));
    numberInService = 1;
    queueLength--;
}

public static void processDeparture(Event e) {
    Event finished = (Event) customers.dequeue();     // the customer description
    if (queueLength > 0) scheduleDeparture();
    else numberInService = 0;

    double response = clock - finished.getTime();     // time in system
    sumResponseTime += response;
    if (response > 4.0) longService++;
    totalBusy += (clock - lastEventTime);
    numberOfDepartures++;
    lastEventTime = clock;
}

چهار چیز را دقیق بخوان:

  1. ورود، خودش ورود بعدی را می‌سازد. سه خط آخر processArrival همان «زنجیره‌ی ورودها»ست. اگر این را فراموش کنی، شبیه‌سازی بعد از مشتری اول می‌ایستد.
  2. صف و خدمت با هم شمرده می‌شوند. هر ورود queueLength++ می‌کند، و اگر سرور بیکار باشد scheduleDeparture() بلافاصله queueLength-- می‌کند. پس بعد از پایان روال، queueLength فقط منتظرهاست. بنابراین maxQueueLength بیشینه‌ی طول خط انتظار است، نه تعداد در سیستم.
  3. انباشت زمان مشغولی مشروط است. totalBusy += clock - lastEventTime فقط وقتی اجرا می‌شود که سرور در آن بازه مشغول بوده: در ورودی که سرور از قبل مشغول بوده، و در هر خروج (چون قبل از خروج قطعاً مشغول بوده). اگر سرور بیکار بوده، هیچ‌چیز اضافه نمی‌شود. این دقیقاً همان شکستن انتگرال $\int B(t)\,dt$ به بازه‌های بین دو رویداد است.
  4. زمان پاسخ از روی شیء مشتری حساب می‌شود. finished.getTime() زمان ورودِ همان مشتری است، پس response زمان در سیستم است (انتظار + خدمت)، نه فقط انتظار.
رابطه · درستی انباشت زمان مشغولی
فرض کن رویدادها در زمان‌های $t_0=0<t_1<\dots<t_m=T$ رخ دهند. چون $B(t)$ بین دو رویداد ثابت است: $$\int_0^T B(t)\,dt=\sum_{k=1}^{m} B(t_{k-1}^+)\,(t_k-t_{k-1})$$ کد دقیقاً همین جمع را می‌سازد: در هر رویداد، اگر سرور در بازه‌ی تمام‌شده مشغول بوده، طول بازه ($\texttt{clock}-\texttt{lastEventTime}$) را اضافه می‌کند و بعد lastEventTime را به‌روز می‌کند. ∎
❌ اشتباه رایج · جابه‌جایی ترتیب دو خط
اگر در processDeparture خط totalBusy += ... را بعد از lastEventTime = clock بگذاری، همیشه صفر اضافه می‌شود و بهره‌وری صفر درمی‌آید. قاعده: اول انباشت، بعد به‌روزرسانی مُهر زمانی. همین خطا در محاسبه‌ی مساحت زیر $Q(t)$ هم رخ می‌دهد.
⚠ نکته‌ی امتحانی · چرا رویداد سومی به نام «شروع خدمت» نداریم؟
در این برنامه «شروع خدمت» رویداد مستقل نیست؛ داخل scheduleDeparture پنهان است و از دو جا صدا زده می‌شود: ورود به سیستم خالی، و پایان خدمت وقتی صف خالی نیست. این کار کد را کوتاه می‌کند ولی یک چیز را از دست می‌دهد: دیگر نمی‌توانی مستقیماً «زمان انتظار» را اندازه بگیری، چون لحظه‌ی شروع خدمت را جایی ثبت نمی‌کنی. در گراف‌های شبیه‌سازی (بخش ۹) Start service یک گره‌ی مستقل است و همین مشکل را حل می‌کند.

06 همان برنامه در پایتون با heapq تکمیلی

ساختار یک‌به‌یک همان جاواست: یک کلاس Event، یک هرم به‌عنوان FEL، و چهار متد. تنها تفاوت واقعی این است که heapq روی لیست کار می‌کند و برای مقایسه از __lt__ استفاده می‌کند.

import heapq, math, random

ARRIVAL, DEPARTURE = 1, 2

class Event:
    __slots__ = ("time", "type", "seq")
    def __init__(self, type_, time, seq=0):
        self.type = type_; self.time = time; self.seq = seq
    def __lt__(self, other):
        return (self.time, self.seq) < (other.time, other.seq)

class Sim:
    def __init__(self, mean_ia=4.5, mean_svc=3.2, total=1000, seed=12345):
        self.mean_ia = mean_ia; self.mean_svc = mean_svc; self.total = total
        self.rng = random.Random(seed)
        self.fel = []; self.customers = []; self.counter = 0

    def exponential(self, mean):                 # inverse transform, like the Java helper
        return -mean * math.log(1.0 - self.rng.random())

    def push(self, ev):                          # futureEventList.enqueue
        self.counter += 1; ev.seq = self.counter
        heapq.heappush(self.fel, ev)

    def initialization(self):
        self.clock = 0.0
        self.queue_length = 0;      self.number_in_service = 0
        self.last_event_time = 0.0; self.total_busy = 0.0
        self.max_queue_length = 0;  self.sum_response_time = 0.0
        self.number_of_departures = 0; self.long_service = 0
        self.push(Event(ARRIVAL, self.exponential(self.mean_ia)))   # the ONE first arrival

    def process_arrival(self, event):
        self.customers.append(event)
        self.queue_length += 1
        if self.number_in_service == 0:
            self.schedule_departure()
        else:
            self.total_busy += self.clock - self.last_event_time
        self.max_queue_length = max(self.max_queue_length, self.queue_length)
        self.push(Event(ARRIVAL, self.clock + self.exponential(self.mean_ia)))
        self.last_event_time = self.clock

    def schedule_departure(self):
        self.push(Event(DEPARTURE, self.clock + self.exponential(self.mean_svc)))
        self.number_in_service = 1
        self.queue_length -= 1

    def process_departure(self, event):
        finished = self.customers.pop(0)
        if self.queue_length > 0:
            self.schedule_departure()
        else:
            self.number_in_service = 0
        response = self.clock - finished.time
        self.sum_response_time += response
        if response > 4.0:
            self.long_service += 1
        self.total_busy += self.clock - self.last_event_time
        self.number_of_departures += 1
        self.last_event_time = self.clock

    def run(self):
        self.initialization()
        while self.number_of_departures < self.total:
            event = heapq.heappop(self.fel)      # getMin + dequeue in one step
            self.clock = event.time
            if event.type == ARRIVAL:
                self.process_arrival(event)
            else:
                self.process_departure(event)
        self.report()

    def report(self):
        rho  = self.total_busy / self.clock
        avgr = self.sum_response_time / self.total
        pc4  = self.long_service / self.total
        print("SINGLE SERVER QUEUE SIMULATION - GROCERY STORE CHECKOUT COUNTER")
        print(f"\tMEAN INTERARRIVAL TIME       {self.mean_ia:10.3f}")
        print(f"\tMEAN SERVICE TIME            {self.mean_svc:10.3f}")
        print(f"\tNUMBER OF CUSTOMERS SERVED   {self.total:10d}")
        print()
        print(f"\tSERVER UTILIZATION           {rho:10.3f}")
        print(f"\tMAXIMUM LINE LENGTH          {self.max_queue_length:10d}")
        print(f"\tAVERAGE RESPONSE TIME        {avgr:10.3f} Time Units")
        print(f"\tPROPORTION > 4 TIME UNITS    {pc4:10.3f}")
        print(f"\tSIMULATION RUNLENGTH         {self.clock:10.3f} Time Units")
        print(f"\tNUMBER OF DEPARTURES         {self.number_of_departures:10d}")

💡 سه نکته‌ی پایتونی که در جاوا پنهان بودند
  • heapq.heappop هم‌زمان کار getMin() و dequeue() را می‌کند و $O(\log n)$ است. اگر FEL را لیست ساده نگه داری و هر بار min بگیری، هزینه $O(n)$ می‌شود و برای میلیون رویداد کُند است.
  • -mean*log(1-u) تبدیل معکوس نمایی است (جلسه‌ی ۱۴ مفصل می‌آید). 1-u به‌جای u نوشته شده تا اگر مولد صفر تولید کرد، log(0) رخ ندهد.
  • customers.pop(0) روی لیست $O(n)$ است؛ برای صف واقعی از collections.deque استفاده کن. برای هزار مشتری فرقی نمی‌کند، برای میلیون چرا.

import heapq, math, random
from abc import ABC, abstractmethod

# ---------- package core ----------
class SimEvent:
    _n = 0
    def __init__(self, dst, time=0.0, src=None, prio=1):
        self.dst, self.time, self.src, self.prio = dst, time, src, prio
        SimEvent._n += 1; self.id = SimEvent._n
    def __lt__(self, o):
        return (self.time, self.prio, self.id) < (o.time, o.prio, o.id)

class SimEntity(ABC):
    def __init__(self, sim_control): self.sim_control = sim_control
    @abstractmethod
    def handle_event(self, event): ...

class SimHeap:                                     # one concrete SimQueue
    def __init__(self): self.h = []
    def schedule(self, event): heapq.heappush(self.h, event)
    def get_next_event(self): return heapq.heappop(self.h)
    def is_empty(self): return not self.h

class SimControl:
    def __init__(self, queue):
        self.queue, self.time, self.end_time = queue, 0.0, math.inf
    def set_run_time(self, t): self.end_time = t
    def get_time(self): return self.time
    def schedule(self, event, delta=None):
        if delta is not None: event.time = self.time + delta
        self.queue.schedule(event)
    def run(self):
        while not self.queue.is_empty():
            event = self.queue.get_next_event()
            if event.time > self.end_time: break
            self.time = event.time
            event.dst.handle_event(event)          # dispatch: the engine knows nothing else

# ---------- package rng ----------
class Exponential:
    def __init__(self, lam, seed=None): self.lam, self.u = lam, random.Random(seed)
    def get_next(self): return -math.log(1.0 - self.u.random()) / self.lam

# ---------- the model: two entities ----------
class MM1Generator(SimEntity):
    def __init__(self, sim_control, dst, rng):
        super().__init__(sim_control)
        self.dst, self.inter_arrival, self.n = dst, rng, 0
        sim_control.schedule(SimEvent(self, prio=2), rng.get_next())    # the initial event
    def handle_event(self, event):
        self.n += 1
        self.dst.new_customer(SimEvent(self.dst, self.sim_control.get_time(), src=self))
        self.sim_control.schedule(SimEvent(self, prio=2), self.inter_arrival.get_next())

class MM1Server(SimEntity):
    def __init__(self, sim_control, rng):
        super().__init__(sim_control)
        self.service_time = rng
        self.queue, self.in_service, self.served = [], False, 0
        self.sum_system = self.sum_queue = self.busy_time = self.last_start = 0.0
    def new_customer(self, event):
        self.queue.append(event)
        if not self.in_service: self.schedule_next_departure()
    def schedule_next_departure(self):
        s = self.service_time.get_next()
        self.sim_control.schedule(SimEvent(self, prio=1), s)
        self.in_service = True
        self.busy_time += s
        self.last_start = self.sim_control.get_time()
    def handle_event(self, event):                 # a departure
        finished = self.queue.pop(0)
        now = self.sim_control.get_time()
        self.sum_system += now - finished.time
        self.sum_queue  += self.last_start - finished.time
        self.in_service = False
        self.served += 1
        if self.queue: self.schedule_next_departure()

08 گراف‌های شبیه‌سازی: قاعده‌ها جزوه امتحانی

جزوه با یک اعتراف صادقانه شروع می‌کند: مدل‌سازی سیستم‌های گسسته‌پیشامد روش استاندارد ندارد و بیشتر شبیه هنر است. گراف‌های شبیه‌سازی تلاشی است برای استانداردکردنش. شروبن (Schruben, 1983) آن‌ها را با نام گراف رویداد (event graph) معرفی کرد و بعداً به گراف شبیه‌سازی تغییر نام دادند.

تعریف ۸.۳ · گراف شبیه‌سازی
گرافی جهت‌دار که:
  • گره = یک رویداد؛ یعنی یک تغییر لحظه‌ای در حالت سیستم. تغییر حالت را داخل آکولاد زیر گره می‌نویسند: {Q++}.
  • یال = زمان‌بندی یک رویداد دیگر. یال از A به B یعنی «وقتی A رخ داد، B را در FEL بگذار».
  • هر یال می‌تواند یک شرط بولی (بالای یال، داخل پرانتز) و یک تأخیر زمانی (زیر یال) داشته باشد.
این تنها الگوی تصویری‌ای است که مستقیماً منطق فهرست رویدادهای آینده را مدل می‌کند؛ نه جریان موجودیت‌ها را، نه فعالیت‌ها را.
رابطه · معنای دقیق یک یال، خط به خط
یالِ $A \xrightarrow[\;t\;]{(i)} B$ دقیقاً یعنی: در انتهای روال رویداد $A$، این کد اجرا شود: $$\texttt{if } (i) \texttt{ then schedule } B \texttt{ at time } \texttt{clock} + t$$ سه نکته‌ی ظریف که در امتحان می‌پرسند:
  • شرط $(i)$ در لحظه‌ی زمان‌بندی سنجیده می‌شود، نه در لحظه‌ی اجرای $B$. اگر حالت بین این دو لحظه عوض شود، $B$ باز هم اجرا می‌شود.
  • تأخیر $t$ می‌تواند خودش یک متغیر تصادفی باشد؛ مقدارش در لحظه‌ی زمان‌بندی تولید و در FEL قفل می‌شود.
  • اگر $A$ چند یال خروجی داشته باشد، همه‌ی شرط‌ها سنجیده می‌شوند و همه‌ی یال‌های برقرار زمان‌بندی می‌کنند — این یک انشعاب «یا» نیست.
💡 چطور یک گراف را بلند بخوانی
هر یال را با این الگو به فارسی بگو: «وقتی [گره مبدأ] رخ داد، اگر [شرط] بود، [گره مقصد] را برای [تأخیر] بعد زمان‌بندی کن». اگر توانستی همه‌ی یال‌ها را این‌طور بخوانی، گراف را فهمیده‌ای. بعد از خواندن، تغییرهای حالت زیر هر گره را هم اضافه کن: «و وقتی اجرا شد، [تغییر حالت] اعمال شود».

09 سه الگوی پایه و رویداد Run جزوه امتحانی

الگوی ۱ · فرایند پواسون

همین گره، همان سه خط آخر processArrival در بخش ۴ است. یال خودزمان‌بند یعنی «زنجیره‌ی ورودها»؛ همان چیزی که کامنت غلط جزوه در بخش ۳ را توضیح می‌داد.

الگوی ۲ · صف ساده G/G/MaxB

نمادها: $t_A$ زمان بین‌ورود، $Q$ تعداد در صف، $B$ تعداد سرور مشغول، $\text{MaxB}$ تعداد کل سرورها، $t_S$ زمان خدمت.

دقت کن که دو یال بین «شروع» و «پایان» خدمت متفاوتاند: یالِ رفت بی‌قیدوشرط است با تأخیر $t_S$ (هر خدمتی که شروع شود، تمام می‌شود)، و یالِ برگشت شرط $(Q>0)$ دارد و تأخیر ندارد (مشتری بعدی بلافاصله شروع می‌شود).

الگوی ۳ · مقداردهی اولیه و رویداد Run

تعریف ۸.۴ · قاعده‌ی رویدادهای اولیه
هر رویدادی که هیچ یال ورودی از گره‌های دیگر ندارد — یعنی تنها یال ورودی‌اش یال خودزمان‌بند خودش است، یا اصلاً یال ورودی ندارد — باید در ابتدای اجرا دستی در FEL گذاشته شود. به‌عنوان قرارداد، یک رویداد ویژه به نام Run ساخته می‌شود که سه کار مقداردهی اولیه را انجام می‌دهد: تنظیم پارامترها، تنظیم مقدار اولیه‌ی متغیرهای حالت، و گذاشتن اعلان‌های رویداد اولیه.

چرا این قاعده کار می‌کند؟ گرهی که هیچ گره‌ی دیگری زمان‌بندی‌اش نمی‌کند، هرگز به‌خودیِ‌خود در FEL قرار نمی‌گیرد، پس باید دستی کاشته شود. در گراف صفِ بالا پیش از افزودن Run، تنها یال ورودیِ Arrival همان یال خودزمان‌بند خودش بود؛ پس اولین ورود هرگز رخ نمی‌داد و FEL از ابتدا خالی می‌ماند. Start service (از Arrival و از End) و End service (از Start) یال ورودی از گره‌های دیگر دارند، پس کاشته نمی‌شوند. با افزودن Run، حالا خودِ Run تنها گرهِ بدون یال ورودی است و تنها چیزی است که مقداردهی اولیه باید در FEL بگذارد.

❌ جمله‌ی مبهم جزوه
متن اسلاید (ص ۷۰) می‌نویسد: «Every event that has only incoming or self-scheduling edges must be scheduled at the beginning of the run». خوانده‌ی تحت‌اللفظی‌اش («هر رویدادی که فقط یال ورودی دارد») غلط است: End service در گراف‌های راه ۱ بخش ۱۰ تقریباً همین وضع را دارد ولی قطعاً نباید کاشته شود. منظور درست همان است که در تعریف بالا آمد: گرهی که هیچ یال ورودی از گره‌ی دیگری ندارد. اگر این را با خودِ گراف صف محک بزنی، فوراً معلوم می‌شود کدام خوانش درست است.
⚠ نکته‌ی مهم · یال با تأخیر صفر و قاعده‌ی تساوی افزوده

جزوه این را نمی‌گوید ولی بدون آن گراف درست پیاده نمی‌شود. یال‌های بدون تأخیر رویدادی را در همین ساعت در FEL می‌گذارند، پس چند رویداد هم‌زمان می‌شوند و ترتیبشان نتیجه را عوض می‌کند. مثال با $\text{MaxB}=1$:

در لحظه‌ی $t=6$، فهرست شامل End@6 و Arrival@6 است و $Q=1$، $B=1$.

  1. End اجرا می‌شود: $B=0$؛ چون $Q>0$، یک Start@6 زمان‌بندی می‌شود.
  2. حالا اگر Arrival@6 قبل از Start@6 اجرا شود: $Q=2$ و شرط $B<\text{MaxB}$ یعنی $0<1$ درست است (چون Start هنوز اجرا نشده)، پس یک شروع خدمت دوم هم زمان‌بندی می‌شود.
  3. نتیجه: هر دو Start اجرا می‌شوند و $B=2$ می‌شود، در حالی که فقط یک سرور داریم. سیستم بی‌سروصدا خراب می‌شود.

قاعده‌ی درست: رویدادهای حاصل از یال‌های بدون تأخیر باید بالاترین اولویت را میان هم‌زمان‌ها داشته باشند. اولویتی که در این صفحه و در کد بخش ۱۲ به کار می‌رود: Run < Start < End < Arrival. با این ترتیب، Start@6 اول اجرا می‌شود، $B$ به ۱ می‌رسد و شرط ورودِ بعدی درست سنجیده می‌شود.

  • بی‌تابی مشتری را روشن کن (بخش ۱۱): حالا هر ورود یک Renege هم زمان‌بندی می‌کند، و هر شروع خدمت آن را از FEL حذف می‌کند. شکیبایی را کم کن تا مشتری‌ها شروع به رفتن کنند.

کجا لازم می‌شود؟

بی‌تابی مشتری (reneging)مشتری هنگام ورود یک «رفتن» برای $t_P$ بعد زمان‌بندی می‌کند؛ اگر خدمتش زودتر شروع شود، آن رفتن لغو می‌شود.
خرابی دستگاهرویداد خرابی، «پایان خدمت» زمان‌بندی‌شده را لغو می‌کند و بعد از تعمیر دوباره زمان‌بندی‌اش می‌کند.
مهلت زمانی (timeout)بسته‌ی شبکه هنگام ارسال یک timeout زمان‌بندی می‌کند؛ رسیدن ACK آن را لغو می‌کند.
لغو سفارشمشتری سفارشی داده که تحویلش زمان‌بندی شده؛ رویداد «انصراف» آن تحویل را از FEL برمی‌دارد.
⚠ نکته‌ی امتحانی · «اولین وقوع بعدی» کافی نیست
تعریف جزوه می‌گوید «اولین وقوع بعدی B حذف شود». وقتی چند نمونه‌ی B هم‌زمان در FEL باشند — مثلاً ده مشتریِ بی‌تاب با ده مهلت متفاوت — این تعریف مبهم است: کدام‌یک؟ در عمل دو راه داری:
  • با ویژگی: یال لغوکننده هم ویژگی می‌برد و موتور، اعلانی را حذف می‌کند که ویژگی‌اش بخورد (مثلاً شناسه‌ی همان مشتری). این راه همیشه درست است.
  • با استدلال ساختاری: در صف FIFO با شکیبایی یکسان، مشتریِ سرِ صف زودترین مهلت را دارد، پس «نزدیک‌ترین Renege در FEL» دقیقاً مال همان کسی است که دارد وارد خدمت می‌شود. در این حالت تعریف ساده هم جواب می‌دهد — ابزار بخش ۹ از همین استدلال استفاده می‌کند.
اگر شکیبایی‌ها متفاوت باشند، راه دوم غلط می‌شود.
💡 لغو در برابر شرط: کدام را به کار ببرم؟
اگر می‌توانی تصمیم را به لحظه‌ی اجرا موکول کنی، شرط ارزان‌تر است: رویداد را زمان‌بندی کن و در ابتدای روالش یک «اگر هنوز معتبر است» بگذار (الگوی stale event). لغو وقتی لازم است که خودِ ماندنِ رویداد در FEL معنا داشته باشد — مثلاً چون می‌خواهی تعداد رویدادهای معلق محدود بماند، یا چون شرطِ اعتبار را نمی‌شود از روی حالت فعلی بازسازی کرد.

    """Nodes are events (a state change); edges are scheduling with a condition and a delay."""
    def __init__(self, nodes, prio, state):
        self.nodes, self.prio, self.S = nodes, prio, state
        self.fel, self.clock, self.seq = [], 0.0, 0

    def schedule(self, name, t, a=None):
        self.seq += 1                                  # tie-break: first scheduled, first out
        heapq.heappush(self.fel, (t, self.prio[name], self.seq, name, a))

    def cancel(self, name, a=None):                    # the dashed edge
        for e in sorted(self.fel):
            if e[3] == name:
                self.fel.remove(e); heapq.heapify(self.fel); return True
        return False                                   # nothing scheduled -> nothing happens

    def run(self, start="Run", end=math.inf):
        self.schedule(start, 0.0)                      # the one event planted by hand
        while self.fel:
            t, _, _, name, a = heapq.heappop(self.fel) # imminent event
            if t > end: break
            self.clock = t                             # advance the clock
            change, edges = self.nodes[name]
            change(self, a)                            # execute the {...} under the node
            for e in edges:                            # follow every outgoing edge
                if e.cond and not e.cond(self, a): continue
                b = e.attr(self, a) if e.attr else a
                if e.cancel: self.cancel(e.target, b)
                else:        self.schedule(e.target, t + (e.delay(self, a) if e.delay else 0.0), b)

📝 راهنمای تمرین ۳ · سؤال ۸ (دو صف متوالی)

سؤال یک برنامه می‌خواهد، نه یک جدول دستی. این‌جا معماری و ساختار داده را می‌گویم؛ عددهای خود سؤال را خودت باید دربیاوری.

  1. قراردادها را اول بنویس. ورود اول در لحظه‌ی صفر. افق هر اجرا تا خروج آخرین مشتری از مرحله‌ی دوم (یک $T$ مشترک برای هر دو سرور، چون سؤال «بهره‌برداری هر سرور بر همین افق مشترک» خواسته). پایان خدمت ۱ = ورود به صف ۲، بدون تأخیر. هر دو صف نامحدود و FIFO، سیستم ابتدا خالی.
  2. دو راه پیاده‌سازی، هر دو قابل قبول:
    • بازگشتی ساده (توصیه‌شده برای شروع). چون صف‌ها FIFO و سرورها تک‌نفره‌اند، نیازی به FEL نداری: برای هر مشتری $k$ فقط دو عدد نگه دار، $\text{free}_1$ و $\text{free}_2$، و بنویس $$b_{1,k}=\max(a_k,\,\text{free}_1),\quad e_{1,k}=b_{1,k}+s_{1,k},\quad b_{2,k}=\max(e_{1,k},\,\text{free}_2),\quad e_{2,k}=b_{2,k}+s_{2,k}$$ این دقیقاً تابع tandem مثال ۸.۲ است و در ۱۵ خط تمام می‌شود.
    • با گراف رویداد. همان دیکشنری nodes بالا با $N=2$ و $\text{MaxB}(j)=1$. گران‌تر است ولی نشان می‌دهد روش عمومی را بلدی، و اگر سؤال بعدی صف محدود یا سرور دوم اضافه بخواهد، فقط یک عدد عوض می‌شود.
  3. ساختار داده‌ی خروجی. برای هر اجرا یک جدول $200\times9$: شماره، ورود، شروع ۱، پایان ۱، شروع ۲، پایان ۲، $W_1$، $W_2$، زمان در سیستم. سؤال صریحاً جدول ده مشتری اول و داده‌ی خام می‌خواهد، پس این جدول را برای حداقل یک اجرا ذخیره کن (CSV).
  4. تولید ورودی‌ها. بین‌ورود از $\{1,2,3,4\}$ با احتمال برابر، خدمت ۱ از $\{1,2,3\}$ با $(0.3,0.4,0.3)$ و خدمت ۲ از $\{1,2\}$ با $(0.6,0.4)$ — هر سه با تبدیل معکوس روی تجمعی. سؤال می‌گوید بذر و مقادیر تولیدشده را ذخیره کن: یک random.Random(seed) با بذر ثابت بساز و هر سه بردار را در فایل بنویس تا نتیجه بازتولیدپذیر باشد. برای ۳۰ تکرار مستقل، بذرهای متفاوت (یا یک جریان پیوسته) بگیر؛ این‌جا برخلاف جلسه‌ی ۵ اعداد مشترک نمی‌خواهیم، چون چیزی را مقایسه نمی‌کنیم.
  5. شاخص‌های هر اجرا. میانگین $W_1$، میانگین $W_2$، میانگین زمان در سیستم، $\rho_1=\sum s_{1,k}/T$، $\rho_2=\sum s_{2,k}/T$، و میانگین زمانی طول هر صف $L_j=\frac1T\int_0^T Q_j(t)\,dt$. برای $L_j$ لازم نیست پلکان را بسازی: $\int Q_j = \sum_k W_{j,k}$، پس $L_j=\big(\sum_k W_{j,k}\big)/T$.
  6. دو کنترل صحتی که سؤال خواسته. (الف) موازنه: تعداد ورودها به هر مرحله و خروج‌ها از آن هر دو ۲۰۰ باشد، و در پایان هر دو صف و هر دو سرور خالی. (ب) برابری $\sum_k W_{j,k}$ با مساحت زیر $Q_j(t)$. برای (ب) ارزشش را دارد که یک بار مساحت را مستقل هم حساب کنی (از روی رویدادهای ورود/خروج صف و مُهر زمانی قبلی) و با جمع انتظارها مقایسه کنی؛ اگر از همان فرمول بسازی، آزمون بی‌معنی می‌شود.

  8. تحلیل گلوگاه. میانگین خدمت‌ها را با میانگین بین‌ورود مقایسه کن و بگو کدام سرور $\rho$ بزرگ‌تری دارد؛ بعد نشان بده همان سرور $W$ و $L$ بزرگ‌تری هم می‌سازد. یک جمله هم درباره‌ی این بنویس که چون سیستم خالی شروع می‌شود و فقط ۲۰۰ مشتری دارد، این عددها حالت پایدار نیستند.
  9. تله‌ها. (۱) مخرج بهره‌وری را برای هر دو سرور یکی بگیر ($T$ مشترک)، نه «آخرین خروج از همان مرحله». (۲) $W_2$ را از پایان خدمت ۱ بگیر، نه از زمان ورود به سیستم. (۳) ورودها به مرحله‌ی دوم ورود مستقل نیستند؛ نباید برایشان بین‌ورود تازه تولید کنی. (۴) اگر از گراف استفاده می‌کنی، قاعده‌ی تساوی بخش ۹ را رعایت کن وگرنه ممکن است یک سرور دو مشتری هم‌زمان بگیرد.

تمرین ۱🟢 گرم‌کردن
در گراف صف ساده‌ی بخش ۹، کدام یال‌ها شرط دارند و کدام‌ها تأخیر؟ هر یال را به فارسی بخوان.
راه‌حل چهار یال داریم. (۱) Run → Arrival: بدون شرط، تأخیر $t_A$ — «وقتی اجرا شروع شد، اولین ورود را برای $t_A$ بعد زمان‌بندی کن». (۲) Arrival → Arrival (خودزمان‌بند): بدون شرط، تأخیر $t_A$. (۳) Arrival → Start service: شرط $(B<\text{MaxB})$، بدون تأخیر — «اگر سروری آزاد است، خدمت را همین حالا شروع کن». (۴) Start → End: بدون شرط، تأخیر $t_S$. (۵) End → Start: شرط $(Q>0)$، بدون تأخیر. پس دو یال شرط دارند و سه یال تأخیر؛ هیچ یالی هر دو را ندارد.
تمرین ۲🟢 گرم‌کردن
در گراف زیر کدام رویدادها باید در ابتدای اجرا در FEL گذاشته شوند؟ گره‌ها: $A$ با یال خودزمان‌بند و یالی به $B$؛ $B$ با یالی به $C$؛ $C$ با یالی به $B$؛ و $D$ که فقط یالی به $A$ دارد.
راه‌حل قاعده‌ی تعریف ۸.۴: هر گرهی که فقط یال ورودی یا خودزمان‌بند دارد باید کاشته شود. $B$ و $C$ از هم یال ورودی دارند، پس نه. $A$ یال ورودی از $D$ دارد، پس نه. $D$ هیچ یال ورودی ندارد، پس فقط $D$ باید در ابتدا در FEL باشد. $D$ همان نقش Run را دارد. توجه: اگر $D$ نبود، $A$ فقط یال خودزمان‌بند داشت و باید خودش کاشته می‌شد.
تمرین ۳🟡 تمرین
در کد جاوای بخش ۴، چه می‌شود اگر در processArrival خط lastEventTime = clock را حذف کنی؟ عدد بهره‌وری چه تغییری می‌کند — بیشتر، کمتر یا نامعلوم؟
راه‌حل lastEventTime دیگر فقط در خروج‌ها به‌روز می‌شود. پس در هر ورودی که سرور مشغول باشد، بازه‌ی $(\texttt{lastEventTime},\texttt{clock})$ بیش از حد واقعی است و بخش‌هایی از زمان چند بار شمرده می‌شوند. نتیجه: totalBusy و در نتیجه $\rho$ بیشتر از مقدار درست می‌شود و حتی می‌تواند از ۱ بگذرد. یک تست خوب برای کدت: اگر $\rho>1$ دیدی، تقریباً همیشه خطای مُهر زمانی است، نه خطای مدل.
تمرین ۴🟡 تمرین

(ب) چون در M/M/1 زمان انتظار = زمان در سیستم منهای زمان خدمت است، زمان خدمت تولیدشده را هم ذخیره کن و در خروج کم کن. راه (الف) تمیزتر است و دقیقاً همان کاری است که گره‌ی Start service در گراف می‌کند. این نشان می‌دهد چرا گراف آن گره را جدا نگه می‌دارد.
تمرین ۵🟡 تمرین
گراف یک صف با ظرفیت محدود بکش: اگر در لحظه‌ی ورود $Q = K$ باشد، مشتری وارد نمی‌شود (balking) و فقط شمارنده‌ی Lost یکی زیاد می‌شود.
راه‌حل گره‌ی Arrival دیگر نباید بی‌قیدوشرط $Q{+}{+}$ کند. راه تمیز: تغییر حالتِ زیر Arrival را خالی بگذار و دو یالِ بدون تأخیر از آن بکش: یکی به گره‌ی تازه‌ی Enter با شرط $(Q+B<K)$ و تغییر حالت $\{Q{+}{+}\}$، و دیگری به گره‌ی Balk با شرط $(Q+B\ge K)$ و تغییر حالت $\{\text{Lost}{+}{+}\}$. یال خودزمان‌بند $t_A$ روی Arrival می‌ماند و یال شرطی $(B<\text{MaxB})$ از Enter به Start service می‌رود. نکته: چون هر دو یال تأخیر صفر دارند و شرط‌هایشان مانعةالجمع است، دقیقاً یکی زمان‌بندی می‌شود.
تمرین ۶🟡 تمرین

تمرین ۷🔴 تحلیلی

راه‌حل درستی: $B$ فقط در Start زیاد می‌شود. هر Start وقتی زمان‌بندی شده که $B<\text{MaxB}$ بوده (یال از Arrival) یا $B$ تازه یکی کم شده بوده (یال از End). با قاعده‌ی تساوی، هیچ Startی در FEL معلق نمی‌ماند تا رویداد دیگری در همان ساعت شرط را از روی $B$ کهنه بسنجد: به‌محض زمان‌بندی، بلافاصله اجرا می‌شود. پس بین سنجش شرط و اعمال $B{+}{+}$ هیچ رویداد دیگری فاصله نمی‌اندازد و ناوردا حفظ می‌شود.
نقض: $\text{MaxB}=1$، $B=1$، $Q=1$ و در لحظه‌ی $t$ هم End و هم Arrival در FEL. اگر ترتیب End → Arrival → Start → Start باشد: End می‌دهد $B=0$ و یک Start می‌کارد؛ Arrival می‌بیند $B=0<1$ و Start دوم را می‌کارد؛ دو Start اجرا می‌شوند و $B=2>\text{MaxB}$.
تمرین ۸🔴 تحلیلی
یال لغوکننده‌ای از Start service به Renege داریم (بی‌تابی مشتری). فرض کن شکیبایی هر مشتری متفاوت و تصادفی است. چرا قاعده‌ی «اولین وقوع بعدی را حذف کن» غلط می‌شود؟ مثال عددی بده و راه درست را بنویس.
راه‌حل با شکیبایی‌های متفاوت، ترتیب مهلت‌ها لزوماً ترتیب ورود نیست. مثال: مشتری A در $t=0$ با شکیبایی ۱۰ (مهلت ۱۰) و مشتری B در $t=2$ با شکیبایی ۳ (مهلت ۵). صف FIFO است، پس وقتی سرور در $t=4$ آزاد می‌شود، A وارد خدمت می‌شود، ولی نزدیک‌ترین Renege در FEL مال B است (۵ در برابر ۱۰). قاعده‌ی ساده، مهلت B را حذف می‌کند و B دیگر هرگز نمی‌رود، در حالی که مهلت A در ۱۰ باقی می‌ماند و بعداً مشتری‌ای را که دارد خدمت می‌گیرد «بی‌تاب» می‌کند. راه درست: یال لغوکننده ویژگی ببرد (شناسه‌ی مشتری) و موتور اعلانی را حذف کند که ویژگی‌اش بخورد — یعنی cancel("Renege", id) به‌جای cancel("Renege"). راه جایگزین: Renege را لغو نکن و در ابتدای روالش بررسی کن که آیا آن مشتری هنوز در صف است یا نه (الگوی رویداد کهنه).
تمرین ۹🔴 تحلیلی
در بخش ۷ دیدی که اجرای ۴۷ هزار مشتری، $S=13.23$ داد در برابر نظریه‌ی ۱۳٫۴۲، و میانگین ۱۲ تکرار ۱۳٫۳۴ با انحراف معیار بین‌اجرایی ۰٫۳۲ شد. (الف) بازه‌ی اطمینان ۹۵٪ را بساز. (ب) چند تکرار لازم است تا نیم‌پهنا به ۰٫۱ برسد؟
راه‌حل (الف) $t_{0.975,11}=2.201$، پس نیم‌پهنا $=2.201\times0.32/\sqrt{12}=0.203$ و بازه $[13.14,\,13.55]$ است. نظریه‌ی ۱۳٫۴۲ داخل بازه است، پس شواهدی بر خطای برنامه نداریم.
(ب) نیم‌پهنا با $1/\sqrt{R}$ کم می‌شود: $0.203\sqrt{12/R}\le0.1$ ⇒ $R\ge12(0.203/0.1)^2\approx49.5$، یعنی حدود ۵۰ تکرار (و با $t$ کمی کوچک‌تر در درجات آزادی بیشتر، کمی کمتر). نکته‌ی عملی: چهار برابر کردن تکرارها فقط نصف کردن پهناست؛ برای دقت بیشتر معمولاً کاهش واریانس (جلسه‌ی ۵) ارزان‌تر از افزایش $R$ است.
تمرین ۱۰🔵 پژوهشگر
گراف شبیه‌سازی را برای یک سیستم با خرابی دستگاه بکش: سرور در حال خدمت می‌تواند خراب شود؛ آن‌گاه «پایان خدمت» زمان‌بندی‌شده لغو می‌شود، تعمیر $t_R$ طول می‌کشد و بعد از تعمیر خدمتِ همان مشتری از نو شروع می‌شود. چه چیزی در این مدل ذاتاً نمی‌تواند با گراف بیان شود؟
راه‌حل گره‌ها: Arrival، Start، End مثل قبل، به‌علاوه‌ی Fail با $\{B{-}{-},\ \text{up}=0\}$ و Repair با $\{\text{up}=1\}$. یال‌ها: Start → Fail با تأخیر $t_F$ (زمان تا خرابی) و شرط $(\text{up}{=}1)$؛ Fail ⇢ End خط‌چین (لغو پایان خدمتِ معلق)؛ Fail → Repair با تأخیر $t_R$؛ Repair → Start بدون تأخیر با شرط «مشتری ناتمام هست». همچنین باید End → Fail خط‌چین اضافه کنی تا وقتی خدمت سالم تمام شد، خرابیِ زمان‌بندی‌شده‌ی آن خدمت لغو شود.
محدودیت: «از نو شروع شدن خدمت» یعنی باید بدانیم چقدر از خدمت انجام شده بود یا نه — و اگر مدل «ادامه از همان‌جا» (preemptive-resume) باشد، باید زمان باقی‌مانده‌ی خدمت را نگه داری. گراف شبیه‌سازی چنین حافظه‌ای برای موجودیت‌ها ندارد؛ تمرکزش روی رویدادهاست و مدل‌ساز باید از موجودیت‌ها انتزاع کند. همین ضعف را خودِ جزوه در جمع‌بندی ص ۷۷ می‌گوید: «تمرکز روی رویدادهاست و مدل‌ساز باید از موجودیت‌ها انتزاع کند». راه عملی: زمان باقی‌مانده را به‌عنوان ویژگی روی یال‌های Repair → Start منتقل کن.

15 جمع‌بندی و اصطلاح‌نامه

۶ چیزی که باید یادت بماند
  1. هر برنامه‌ی زمان‌بندی رویداد چهار بخش دارد: برنامه‌ی اصلی، مقداردهی اولیه، یک روال برای هر رویداد، و گزارش‌گیر. حلقه‌ی اصلی فقط سه کار می‌کند: کم‌ترین زمان را بردار، ساعت را روی آن بگذار، روال را صدا بزن.
  2. آماره‌های زمانی (بهره‌وری، میانگین طول صف) با مُهر زمانی رویداد قبلی ساخته می‌شوند: اول $\texttt{acc} \mathrel{+}= \texttt{مقدار}\times(\texttt{clock}-\texttt{lastEventTime})$، بعد به‌روزرسانی مُهر. جابه‌جایی این دو خط، آماره را صفر یا متورم می‌کند.
  3. چارچوب شیءگرا فقط یک چیز را عوض می‌کند و همان یک چیز همه‌چیز است: رویداد به‌جای «نوع»، مقصد دارد، و موتور به‌جای if/else روی نوع، handleEvent مقصد را صدا می‌زند.
  4. در گراف شبیه‌سازی، گره = رویداد (تغییر حالت) و یال = زمان‌بندی. هر یال می‌تواند شرط، تأخیر، ویژگی و حالت لغو داشته باشد. شرط در لحظه‌ی زمان‌بندی سنجیده می‌شود، نه اجرا.
  5. هر گرهی که فقط یال ورودی یا خودزمان‌بند دارد باید در ابتدا کاشته شود؛ قرارداد، رویداد Run است که پارامترها، حالت اولیه و رویدادهای اولیه را می‌گذارد.
  6. یال‌های بدون تأخیر رویداد هم‌زمان می‌سازند. بدون قاعده‌ی تساوی صریح (Start قبل از بقیه) مدل بی‌سروصدا خراب می‌شود و مثلاً $B$ از $\text{MaxB}$ می‌گذرد.
⏭ برای جلسه‌ی بعد
تا این‌جا هر جا «زمان بین‌ورود نمایی با میانگین ۴٫۵» گفتیم، فرض کردیم چنین توزیعی وجود دارد و می‌شود از آن نمونه گرفت. جلسه‌ی ۹ (فصل ۵) برمی‌گردد به مبانی: متغیر تصادفی، امید، واریانس، کوواریانس و قضیه‌ی حد مرکزی — همان ابزاری که بازه‌های اطمینان این صفحه را توجیه می‌کند. قبلش یک بار تعریف $E[X]$ و $\operatorname{Var}(X)$ را برای حالت گسسته و پیوسته مرور کن.
